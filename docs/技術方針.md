# 技術方針

## 1. 配るものは exe 1個に揃える（2026-10-10 改訂）

当初は「電カルPCは C#、手持ちPCは Python」と分けたが、案件001 の導入でクリニック側に Python を入れてもらう手間
（インストール、Microsoft Store の偽 python、仮想環境）が最大のハードルだと分かった。以後は次に揃える。

| 動かす場所 | 言語・形 | 理由 |
|---|---|---|
| 手持ちPC（インターネット側） | **C# (.NET 8) self-contained の exe 1個** + config.json + bat | クリニック側のインストールが不要。Web 操作は Playwright for .NET で、ブラウザは Windows 標準の Edge（`Channel = "msedge"`）を使うのでブラウザのダウンロードも不要 |
| 電カルネットワークのPC（閉域） | C# (.NET 8 self-contained) の exe 1個、または .NET Framework 4.8 | 同上。閉域でもコピーだけで動く |
| 超小物（ファイル整理・印刷） | PowerShell | Windows 標準。bat から呼ぶ |
| 開発者の手元 | Python 可 | 試作・検証は速い。ただし配る形にはしない |

exe は 70MB 前後（ランタイム同梱）、Playwright のドライバ（node.exe）が 90MB 前後。zip で 60MB 程度。
配布フォルダは GitHub Actions（`.github/workflows/build-001-cs.yml`）で自動ビルドし、Artifacts からダウンロードする。

## 2. 「電カル／予約システムを操作する」の実態は3パターン

日本の電カルは公開 API がほぼ無い。実際に取れる手段で考える。優先順位は **ファイル連携 > API > ブラウザ自動化 > 画面操作**。

1. **ファイル連携**（CSV 出力、SS-MIX2、ORCA API）。最も壊れにくい。
2. **クラウド型（ブラウザで動く電カル・予約システム）**。Playwright でブラウザ自動化。SPA の場合は DOM を読むより、裏で呼ばれている JSON API の応答を横取りする方が安定する。
3. **オンプレ型（Windows アプリ）**。C# + FlaUI（UI Automation）で画面部品を直接つかむ。

## 3. AI の使いどころ

- 実行時に AI は使わない。プログラムは決定的に動く。
- AI を使うのは開発時のみ（Claude Code がコードを書く、画面構造を読む）。
- 実行時に AI が必要な案件（手書き読取、自由記述の要約・分類、文案生成）は、3省2ガイドラインの観点から閉域網から外部 AI へ患者情報を送る構成を避ける。手持ちPCで個人情報を除いてから使うか、人が転記する。

## 4. 配布・運用

- 手持ちPC: exe 1個のフォルダを置く。定期実行は Windows タスクスケジューラ。
- 電カルPC: exe 1個 + 設定ファイル1個。管理者権限を要求しない。ベンダーに事前に一言入れる。
- 認証情報は環境変数または `local/` 配下のファイル。リポジトリには入れない。

## 5. 外部サービスを自動操作するときの確認事項

- 利用規約で自動アクセスが禁止されていないか。
- CSV 出力や API があればそちらを優先し、サポートに有無を問い合わせる。
- 画面を見る頻度は必要最小限（数分〜1時間に1回程度）。
